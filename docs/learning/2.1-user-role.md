## Real-world example

A delivery company has an admin, a dispatcher, and drivers. Think of an enum as
the official list of job titles. It gives code a fixed set of named choices.
It does not decide what each employee is allowed to do; policies do that later.
Customers track parcels publicly, so the blueprint does not define a customer role.

## Every line of UserRole.php

```php
<?php

namespace App\Enums;

enum UserRole: string
{
    case Admin = 'admin';
    case Dispatcher = 'dispatcher';
    case Driver = 'driver';
}
```

- Line 1: starts PHP code.
- Lines 2 and 4: blank lines separate the parts for readability.
- Line 3: gives the enum its namespace. Composer maps `App` to `app/`.
- Line 5: declares an enum named UserRole. `: string` gives each case a string value.
- Line 6: opens its body.
- Line 7: declares the Admin case with the backing value `admin`.
- Line 8: declares the Dispatcher case with the backing value `dispatcher`.
- Line 9: declares the Driver case with the backing value `driver`.
- Line 10: closes its body.

`UserRole::Driver` is an enum case object. `UserRole::Driver->value` is the string
`driver`. `::` accesses the enum's case or static method; `->` accesses the case's
property. No `new UserRole()` is needed or allowed.

## Converting values

```php
$role = UserRole::from('driver');
$storedValue = $role->value;
```

Flow: the string `driver` becomes the Driver case, then `->value` returns `driver`.
This is useful when reading and writing data. This task adds no database column
or Eloquent cast yet; those need their roadmap implementation.

`from()` throws ValueError when a string is unknown. `tryFrom()` returns null
instead. Both require an exact string match: `Admin` and ` driver ` are invalid.
`tryFrom()` is not a full request validator: callers still need to check input
types and authorization. Even the valid string `admin` is not permission to become
an admin. See the [PHP enum manual](https://www.php.net/manual/en/language.enumerations.backed.php).

## Why this design?

The blueprint requires roles to live in enums or configuration instead of magic
values spread through the code. String values also match its database role names.
A class containing string constants would leave variables free to contain any
string; a parameter typed as UserRole accepts the defined enum cases.
We kept this enum focused on role identities, with no labels, permissions, or
framework dependencies. Translated labels belong to the frontend translation work.

Good approach, teaching example:

```php
$role = UserRole::Driver;
```

Fragile alternative, teaching only:

```php
$role = 'dirver';
```

The typo is still a valid PHP string but is not a supported role. A later comparison
with `driver` would fail. Using the enum case avoids repeating these strings.

## Walk through the test file

- `namespace Tests\Unit` places the test in the unit-test namespace.
- The `use` statements import our enum, PHPUnit's DataProvider attribute and
  TestCase, and ValueError.
- `extends TestCase` supplies PHPUnit assertions without booting Laravel or a database.
- The first method calls `cases()` to list every case. `array_map` converts each
  case to its value; `fn` declares a short function. Its parameter and return types
  specify a UserRole input and a string output. `assertSame` checks the exact list.
- The second method converts each stored string and checks the exact case identity.
- The third receives a string from `invalidRoleValues`. The DataProvider attribute
  tells PHPUnit to run it once per data row. `assertNull` checks rejection by
  `tryFrom()`. The provider gives unknown, differently capitalized, padded, and
  empty strings descriptive names. Its PHPDoc describes rows containing one string.
- The fourth declares an expected ValueError, then attempts strict conversion of
  `customer`. It fails if conversion succeeds or throws the wrong exception.
- Braces open and close the class and methods; semicolons end statements.

These tests protect the agreed role vocabulary and conversion behavior, including
invalid inputs. They do not prove authorization, HTTP validation, or persistence.
