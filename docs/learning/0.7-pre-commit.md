# 0.7 — فحص الأسرار قبل commit

## الملفات ومسار التنفيذ

أضفنا 4 ملفات وعدّلنا ملفين:

- [.githooks/pre-commit](../../.githooks/pre-commit): ينادي Gitleaks قبل commit.
- [الاختبار](../../tests/scripts/pre-commit-test.sh): يتأكد من الأمر ونتائج النجاح والفشل.
- [SETUP.md](../SETUP.md): طريقة تثبيت الأداة وتفعيل الـhook لكل نسخة من المشروع.
- هذا الدليل: شرح الكود والتدريب.
- .gitignore: يستبعد مجلد الأدوات المحلية .tools.
- TASKS.md: يسجل التقدم وحدود التحقق.

نسخة Gitleaks المحلية ملفات تشغيل خارج Git، وليست كودًا جديدًا كتبناه. إعداد hooksPath محلي داخل Git، ولا ينتقل تلقائيًا لمن يستنسخ المشروع.

## مثال واقعي

تخيّل commit مثل طرد تريد ترسله. staged files هي الأشياء التي وضعتها داخل الطرد. hook هو موظف التفتيش، وGitleaks جهاز الفحص. إذا الجهاز متعطل أو يلقى شيئًا ممنوعًا، لا يسمح الموظف بإرسال الطرد.

المسار: git add → git commit → pre-commit → Gitleaks → نجاح يسمح بالـcommit؛ فشل يمنعه. هذا لا يدخل مسار HTTP أو Laravel.

## شرح ملف hook بالترتيب

- السطر الأول يختار Bash.
- set -euo pipefail يساعد على إيقاف الأخطاء بدل تجاهلها.
- command -v يسأل: هل Gitleaks متوفر في PATH؟ مثل البحث عن جهاز الفحص في المكان المعتاد.
- >/dev/null يخفي نتيجة البحث؛ 2>&1 يخفي رسالة البحث أيضًا. نحن نحتاج نتيجة وجود الأداة فقط، مو اسم مسارها.
- إذا موجود، scanner يحمل اسم الأمر gitleaks.
- else: إذا غير موجود، نجرّب النسخة المحلية الخاصة بهذا المشروع على Windows.
- git rev-parse --show-toplevel يجيب جذر المستودع بدل الاعتماد على المسار الحالي.
- scanner يحمل مسار البرنامج داخل .tools/gitleaks.
- [[ ! -x ... ]] يتحقق أن الأداة غير قابلة للتشغيل.
- echo يوضح لماذا منعنا commit وأين تعليمات الإعداد.
- exit 1 يرجع فشلًا إلى Git، فيتوقف commit.
- fi الأولى تغلق فحص النسخة المحلية، والثانية تغلق اختيار مكان الأداة.
- التعليق يوضح سبب اختيار staged والـredaction.
- exec يستبدل عملية hook بعملية Gitleaks، فيوصل نتيجة الأداة نفسها إلى Git.
- git هو نمط فحص المستودع في Gitleaks، وليس استدعاء أمر git من هذا السطر.
- --pre-commit يختار فحص التغييرات، و--staged يختار النسخة المجهزة للـcommit.
- --redact يخفي قيمة السر في النتائج؛ --no-banner يخفي الشعار فقط.

## شرح الاختبار

نحدد جذر المشروع ثم نتأكد من وجود hook. أول اختبار فشل لأن التنفيذ لم يكن موجودًا.

mktemp ينشئ مكان تجارب؛ trap يحذفه عند النهاية. نكتب برنامجًا صغيرًا باسم gitleaks في مجلد مؤقت ونضعه أول PATH، حتى يناديه hook أثناء الاختبار.

البرنامج التجريبي يسجل arguments في CALL_LOG ثم يرجع SCAN_STATUS. نتحقق أن الأمر يفحص staged ويخفي الأسرار. بعدها نجرب نتيجة 1 (اكتشاف محتمل) و2 (خطأ تشغيل)، وكلاهما لازم يمنع commit. هذا يختبر التوصيل، وليس قدرة جهاز Gitleaks الحقيقي على كشف الأسرار.

## ليش هذا التصميم؟

hook قصير ومسؤوليته تشغيل الفحص فقط. ما نعيد بناء قواعد كشف الأسرار بأنفسنا؛ الأداة المختصة تقوم بها. نفحص staged حتى نراجع ما سيُحفظ فعلًا، وليس نسخة الملف التي قد تكون تغيرت بعد git add.

نسخة سيئة تعليمية:

```bash
gitleaks git --staged || true
```

true يعني نجاح مهما كانت نتيجة الأداة. مثل موظف يشوف إنذار الجهاز ويسمح للطرد يطلع.

نسختنا تمرر النتيجة نفسها عبر exec. كذلك غياب الأداة يمنع commit بدل الادعاء أن الفحص نجح.

## حدود مهمة

Gitleaks يعتمد قواعد كشف، فلا يضمن العثور على كل سر. الـhook محلي ويمكن تجاوزه تقنيًا؛ لذلك نحتاج فحص CI وحماية GitHub لاحقًا. النسخة المحمولة لا تنتقل مع المستودع. وجود سر في تاريخ قديم يحتاج معالجة مستقلة وتدوير السر.

## تمرين مراجعة مؤجل لحين رغبتك

التحقق: نجحت اختبارات توصيل الأمر ونتائج النجاح والفشل، وفحص صيغة Bash وحد الأسطر. ثبتنا النسخة المحمولة بعد مطابقة SHA256 المنشورة. اختبار Git حقيقي داخل مستودع مؤقت سمح بـcommit نظيف ومنع مفتاحًا وهميًا مع إخفاء قيمته. فعّلنا hooksPath محليًا بعد التأكد من عدم وجود hook سابق يتبدّل. لم نفحص تاريخ المستودع كاملًا ولم نضف فحص الأسرار إلى CI بعد.

ماذا يحدث بهذا المثال لو Gitleaks رجع 1؟

```bash
gitleaks git --staged
exit 0
```

افترض أنه لا يوجد set -e. اقترح أصغر تصحيح، ثم اقترح اختبارًا لغياب الأداة.

أسئلة مراجعة: لماذا staged؟ لماذا نخفي القيم في النتائج؟ هل غياب جهاز الفحص يعتبر نجاحًا؟ وهل تفعيل hook ينتقل لمن يسوي clone؟
