# 1.1 — أول هيكل Laravel

## شنو بنينا؟

ثبتنا Laravel 12.69.3 داخل backend. Composer نزّل الهيكل والمكتبات الرسمية؛ ما كتبنا ميزات الشحنات أو المصادقة بعد.

قائمة كل ملفات الهيكل ووظيفة كل ملف موجودة في [inventory](1.1-file-inventory.md). المكتبات داخل vendor والأدوات داخل .tools وإعدادات .env المحلية مستبعدة من Git، ولا تدخل عدد ملفات الكود الجديدة القابلة للرفع.

رتّب القراءة: public/index.php، ثم bootstrap/app.php، ثم routes/web.php، ثم resources/views/welcome.blade.php، ثم tests/Feature/ExampleTest.php. باقي الملفات نراجعها عند استخدامها، وما ندّعي أنك فهمتها كلها بمجرد التثبيت.

## مثال من الحياة ومسار الطلب

تفتح عنوان الصفحة الرئيسية. مثل دخولك شركة:

1. public/index.php هو موظف الاستقبال، يستلم الطلب.
2. Composer autoload هو دليل يعرف أين توجد الكلاسات المطلوبة.
3. bootstrap/app.php يجهّز الشركة: المسارات، الوسطاء، ومعالجة الأخطاء.
4. routes/web.php يختار الرد المناسب لعنوانك.
5. welcome.blade.php يجهّز HTML، والرد يرجع للمتصفح.

هذه بداية المسار فقط. لما نبني API يصير عندنا FormRequest → Controller → Action → Repository → Resource وفق الـBlueprint. الـroute الحالي لا يحتاج كل هذه الطبقات لأنه يعرض صفحة تشغيل بسيطة.

## public/index.php، بالترتيب

- `<?php` يبدأ PHP.
- سطرا use يستوردان أسماء Application وRequest حتى نستخدمها دون كتابة المسار الكامل كل مرة.
- define مع microtime يسجل وقت بداية الطلب لقياس الزمن، ولا يتصل بقاعدة بيانات.
- التعليق ثم if يفحص وجود ملف وضع الصيانة. المتغير maintenance يحتفظ بمساره، وrequire يشغّله إذا موجود.
- `__DIR__` يعني مكان الملف الحالي؛ `../` يرجع مستوى واحدًا.
- require لملف vendor/autoload.php يجهّز تحميل الكلاسات تلقائيًا. مثل دليل أسماء الموظفين ومكاتبهم.
- التعليق `@var Application` يساعد أدوات الفحص تفهم نوع المتغير، ولا ينفّذ كودًا.
- require_once يحمّل bootstrap/app.php مرة واحدة ويحفظ التطبيق الذي يرجعه داخل app.
- Request::capture يقرأ الطلب الحالي، وhandleRequest يجعل Laravel يعالجه ويرسل الرد.
- تعليقات Laravel المولّدة تصف المراحل؛ ليست تعليمات مستقلة. السطر الفارغ يفصل القراءة فقط.

## bootstrap/app.php، بالترتيب

- سطور use تختصر أسماء الكلاسات المستخدمة.
- Application::configure يبدأ إعداد التطبيق ويحدد جذر المشروع عبر dirname(__DIR__).
- withRouting يحدد ملفات مسارات الويب والأوامر، ويضيف مسار الفحص `/up`.
- web يشير إلى routes/web.php؛ commands يشير إلى routes/console.php.
- withMiddleware مكان تخصيص الوسطاء. الوسيط مثل حارس يفحص الطلب قبل وصوله للرد. الدالة الحالية فارغة ولا تضيف قواعد جديدة.
- withExceptions مكان تخصيص التعامل مع الأخطاء، وهو فارغ حاليًا.
- function تستقبل كائنًا بنوع محدد، و`: void` تعني أنها لا ترجع قيمة.
- `->` ينادي دالة على كائن؛ هنا كل خطوة تكمل إعداد الكائن.
- create ينشئ التطبيق، وreturn يعيده إلى index.php أو artisan.

## routes/web.php، كل سطر له وظيفة

```php
<?php

use Illuminate\Support\Facades\Route;

Route::get('/', function () {
    return view('welcome');
});
```

`use` يستورد واجهة Laravel لتسجيل المسارات. get يعني طلب قراءة بطريقة HTTP GET. `/` هو العنوان الجذري. function دالة دون اسم تنفذ عند مطابقة الطلب. return يرجع النتيجة، وview يبحث عن resources/views/welcome.blade.php. الأقواس تغلق الدالة ثم استدعاء Route::get، والفاصلة المنقوطة تنهي التعليمة.

هذا الملف جدول توجيه، وليس مكان قواعد الشحنات. وضع قواعد الشحنات هنا لاحقًا يجعل الاختبار والصيانة أصعب.

## صفحة welcome الصغيرة

اختصرنا الصفحة الرسمية الكبيرة إلى HTML بسيط لأن واجهة المنتج ستكون Next.js، وحتى تكون ملفاتنا صغيرة وسهلة القراءة.

- DOCTYPE يعلن HTML، وhtml يحدد لغة الصفحة من إعداد التطبيق.
- str_replace يحول رمز مثل en_US إلى en-US الذي يناسب HTML.
- head يحتوي معلومات الصفحة. charset يسمح بأحرف العربية وغيرها؛ viewport مناسب لأحجام الأجهزة.
- title وh1 يقرآن اسم التطبيق من config بدل تكرار اسم ثابت.
- body يحتوي المحتوى، وmain يحدد المحتوى الأساسي، وp يوضح أن الباكند يعمل.
- `{{ ... }}` في Blade يعرض القيمة مع escaping. هذا يقلل خطر عرض HTML ضار من النصوص.
- وسوم الإغلاق تنهي العناصر. هذه صفحة تطوير وليست واجهة ثنائية اللغة للمنتج.

## اختبار الصفحة

namespace يضع الكلاس داخل مجموعة Tests\Feature. use يستورد TestCase الذي يشغّل Laravel في الاختبارات. extends يعني أن اختبارنا يرث تجهيز التطبيق من كلاس الاختبار الأساسي.

اسم الدالة يبدأ بـ test حتى يتعرف PHPUnit عليها. this->get('/') يرسل طلبًا داخل بيئة الاختبار، ويحفظ الرد. assertStatus(200) يتأكد من نجاح الرد. لا يثبت أن الصفحة صحيحة بكل التفاصيل أو أن قاعدة البيانات جاهزة.

اختبار Unit الافتراضي يثبت true فقط؛ فائدته هنا التأكد أن أداة الاختبار تعمل، وليس اختبار منطق المشروع.

## ليش اخترنا هذا الهيكل؟

استخدمنا الهيكل الرسمي حتى نتعلم Laravel كما يستخدمه الآخرون، بدون بناء framework خاص. ما أضفنا starter kit حتى المصادقة تأتي ضمن مهام التعلم. الجلسات والكاش المحلية تستخدم ملفات مؤقتًا، حتى ما نحتاج MySQL قبل مهمة Docker.

ملفات User والمهاجرات الافتراضية مولّدة ولم ننفّذ المهاجرات. هذه ليست قاعدة الشحنات النهائية. كذلك API routes وSanctum لم تتم إضافتهما بعد.

## مثال جيد وسيئ

سيئ تعليميًا في صفحة تحتاج تعرض اسم التطبيق كنص:

```blade
{!! config('app.name') !!}
```

هذه الصيغة تعرض HTML دون escaping. إذا القيمة تحتوي HTML ضارًا يمكن أن يتفسر بدل عرضه كنص.

الاختيار المستخدم:

```blade
{{ config('app.name') }}
```

يعرض الاسم كنص escaped. مثال من الحياة: نقرأ محتويات ورقة مستلمة، بدل تنفيذ كل أمر مكتوب فيها.

## تمرين مراجعة، الحل بعد محاولتك

```php
Route::post('/', function () {
    return view('welcome');
});
```

إذا غيّرنا get إلى post، ماذا تتوقع عند فتح `/` من المتصفح؟ هل اختبار this->get('/') يبقى ناجحًا؟ اقترح تصحيحًا أو اختبارًا يوضح المشكلة.

تمرين عملي: اقترح إضافة assertSee لاختبار الصفحة حتى يتحقق من الجملة المعروضة، واشرح ماذا يكشف فوق فحص 200.

أسئلة مقابلة: ما دور autoload؟ لماذا bootstrap منفصل عن routes؟ ما الفرق بين اختبار نجاح الرد واختبار قاعدة البيانات؟ لماذا لا نضع منطق الشحنات داخل هذا route؟

## الفحوص وحدودها

الاختباران الافتراضيان نجحا قبل وبعد اختصار صفحة الترحيب. Composer validate نجح وaudit لم يجد تنبيهات معروفة وقت الفحص. فحص الحد 150 نجح للمسارات المحددة. لا يعني ذلك أن ميزات المشروع مكتملة أو أن MySQL وDocker وCI الباكند جاهزة. Pint وPHPStan في مهام 1.3 و1.4.

لا commit للمهمة 1.1 حتى تقول next أو تطلب صراحة الانتقال حسب البروتوكول. المرجع: https://laravel.com/docs/12.x/lifecycle
