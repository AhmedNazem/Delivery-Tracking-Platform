## Real-world example and planned flow

Think of the session cookie as a visitor badge. The browser stores it and sends
it with requests. A CSRF token is an additional check for requests that change
data. It helps prevent another website from making a logged-in browser perform
an unwanted action. CORS controls which origins may read cross-origin responses.

The future Next.js interface runs at http://localhost:3000; Laravel runs at
http://localhost:8000. Ports make them different origins, but they share a host.
Do not mix localhost and 127.0.0.1 in this workflow.

Planned request flow:

1. Frontend requests GET /sanctum/csrf-cookie with credentials included.
2. Laravel sets the session cookie and XSRF-TOKEN cookie, returning HTTP 204.
3. Frontend sends login data with cookies and the URL-decoded XSRF-TOKEN value
   in an X-XSRF-TOKEN header.
4. Laravel checks CSRF and, once task 2.3 is built, validates login credentials.
5. Authenticated requests use the session cookie; frontend code does not need
   to store a personal access token.

This task implements the foundation and step 1, not login/register/logout.
The CSRF cookie endpoint is provided by Sanctum itself. No migrations were run,
and no token issuing, personal-access-token migration, or HasApiTokens trait was
added because our current requirement is first-party session authentication.
See [Laravel's Sanctum documentation](https://laravel.com/docs/12.x/sanctum).

## config/cors.php walkthrough

`<?php` starts PHP; `return [...]` provides Laravel's configuration array.
Each `=>` maps a setting to its value; commas separate entries.

| Setting | Purpose and reason |
|---|---|
| paths | Applies CORS to api/* and sanctum/csrf-cookie. |
| allowed_methods | Permits the listed HTTP methods, including OPTIONS preflight. |
| allowed_origins | Reads exact frontend URLs from CORS_ALLOWED_ORIGINS. |
| allowed_origins_patterns | Empty: no broad regular-expression origin rules. |
| allowed_headers | Permits Accept, Content-Type, X-XSRF-TOKEN and X-Requested-With. |
| exposed_headers | Empty: no additional response headers exposed to JavaScript. |
| max_age | Zero: no dedicated preflight cache duration. |
| supports_credentials | True: permits browser credential use for allowed origins. |

The origin parsing expression works inside-out: env reads a comma-separated
string, explode splits it, array_map('trim', ...) removes surrounding whitespace,
and array_filter removes empty entries. Example: two frontend URLs separated by
a comma become two allowed origins. An explicitly empty value yields no origins.

With one allowed origin, the CORS library returns that fixed origin even for
a disallowed request. The browser refuses access when it does not match the
requesting origin. CORS is not authentication and does not stop non-browser clients.

## config/sanctum.php walkthrough

The three use statements import middleware classes. `::class` supplies their
fully qualified class names so Laravel can create them.

| Setting | Purpose |
|---|---|
| stateful | Frontend hosts allowed to use stateful API handling. Include ports, omit schemes. |
| guard | Checks Laravel's web session guard. |
| expiration | Null: no global token expiration override; this does not set session lifetime. |
| token_prefix | Retains Sanctum's default optional token-prefix setting. |
| authenticate_session | Supplies Sanctum's session authentication middleware. |
| encrypt_cookies | Supplies Laravel's encrypted-cookie middleware. |
| validate_csrf_token | Supplies Laravel's CSRF middleware. |

The stateful list uses the same split/trim/filter expression as CORS.
Keep the two lists aligned, but note their different formats:

```dotenv
CORS_ALLOWED_ORIGINS=http://localhost:3000
SANCTUM_STATEFUL_DOMAINS=localhost:3000
```

SESSION_DOMAIN=null means host-only cookies. Cookies are not restricted by port.
SESSION_SECURE_COOKIE=false supports local HTTP; set true with production HTTPS.
SESSION_SAME_SITE=lax retains the blueprint's same-site cookie policy. Production
app/API subdomains need an appropriate shared parent cookie domain and HTTPS.

## Test walkthrough

The file imports Route and our Laravel TestCase. Extending TestCase boots the
application. Public methods beginning with test_ are individual test cases.
`$this->withHeader(s)` adds request headers. get/options/postJson send requests;
the chained assert methods check the response and fail when behavior differs.

1. The cookie test checks HTTP 204, both cookies, the allowed origin, and credentials.
2. The preflight test sends OPTIONS, requested method and requested headers. It
   checks browser permission for the allowed frontend without needing a login route.
3. The unknown-origin test checks that the server does not echo that origin as allowed.
4. The missing-token test temporarily changes the application environment from
   testing to local because Laravel ordinarily skips CSRF enforcement in tests.
   It registers a test-only POST route in the API group and expects HTTP 419.
5. The matching-token test sets a session token and matching X-CSRF-TOKEN header,
   then expects HTTP 204. This tests the middleware's token-match branch directly.
   The future browser client will use the allowed X-XSRF-TOKEN header with its
   encrypted cookie value; this test is not a full browser login test.

The probe routes exist only in tests. `fn () => response()->noContent()` is a
short function returning an empty HTTP 204 response. No database is needed here.

## Good and bad practices

Good: list the exact frontend origin and enable credentials for cookie requests.
Bad, teaching only: allow every origin by reflecting any incoming Origin header.
That can expose authenticated responses to websites you did not intend to trust.
Correct the origin allow-list instead of disabling CSRF when a POST returns 419.

Good: retain CSRF middleware and send the required token.
Bad, teaching only: exempt all api/* routes from CSRF to make browser requests work.
That removes an important check from stateful requests which change data.

## Interview questions and hands-on practice

1. Why do CORS origins include a scheme, while Sanctum's stateful hosts do not?
2. What does a successful CSRF-cookie request prove about the user's identity?
3. Why can all tests pass without proving the complete login flow works?

Hands-on: propose a test for a mismatched CSRF token. Predict its status and name
the existing test you would adapt. Do not change the application to accept it.
